## 1. Project Purpose, Architecture & Baseline Setup (Part A)

### 1.1 Project Purpose and Architecture
The target project is **Flask Image Recognition**, a computer vision web application designed to classify hand-sign digit gestures (digits 0 through 9) from user-uploaded images. The system architecture comprises:
1. **Presentation / Web Layer (`app.py`, `templates/`):** A Flask web application handling HTTP routing. The `/` route serves the client interface (`index.html`), while the `/prediction` route accepts `multipart/form-data` image uploads via POST and renders prediction results (`result.html`). Direct GET requests to `/prediction` are handled gracefully with guidance.
2. **Inference & Preprocessing Layer (`model.py`):** Utilizes a pre-trained deep learning convolutional neural network (`digit_model.h5`) trained via transfer learning. The preprocessing pipeline reads input image byte streams, standardizes color profiles to RGB, resizes matrices to $224 \times 224$ pixels, normalizes pixel intensities to $[0.0, 1.0]$, and produces batch-shaped tensors (`(1, 224, 224, 3)`).
3. **Automated Testing Suite:** 17 baseline automated tests spanning unit tests (`test_model.py`), integration tests (`test_integration_happy.py`, `test_integration_sad.py`), and acceptance edge-case tests (`test_acceptance_*.py`) running via `pytest`.

## 2. CI/CD Workflow & Baseline Capture (Part B)

### 2.1 Scanner Scope & Configuration (`sonar-project.properties`)
The scanner configuration was established according to Appendix A:
```properties
sonar.projectKey=Ov3rCl0ckd_Flask_Image_Recognition
sonar.organization=ov3rcl0ckd
sonar.sources=app.py,model.py
sonar.tests=test_model.py,test_acceptance_edge_cases.py,test_acceptance_happy.py,test_acceptance_sad.py,test_integration_happy.py,test_integration_sad.py
sonar.python.coverage.reportPaths=coverage.xml
sonar.sourceEncoding=UTF-8
sonar.exclusions=coverage.xml,conftest.py,digit_model.h5,static/**,templates/**,test_images/**,**/*.md,**/*.txt
```
**Rationale:**
- `sonar.sources` isolates production source files (`app.py`, `model.py`) from test harnesses and static assets.
- `sonar.tests` explicitly registers the pytest test suites so SonarQube recognizes unit and integration tests without treating test assertions as uncovered production logic.
- `sonar.python.coverage.reportPaths` ingests the Cobertura-formatted `coverage.xml` generated by `pytest-cov`.
- `sonar.exclusions` filters binary model weights (`digit_model.h5`), reports, and non-executable markdown/text assets.

The workflow automates dependency installation, automated testing with coverage generation, and cloud scanning on every push to `main`:

```yaml
      - name: SonarQube Cloud scan

        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
```

## 3. Investigation and Prioritization of Findings (Part C)

SonarQube Cloud surfaced distinct actionable quality findings spanning security vulnerabilities, configuration hardening, and maintainability concerns. Four primary findings were selected and prioritized:

### Finding 1: Unrestricted Production Debug Mode
- **Rule ID:** `python:S4507` (*"Make sure this debug feature is deactivated before delivering the code in production"*)
- **Category & Severity:** Security Vulnerability / Severity: Minor (Software Quality: Security / Low Impact).
- **Location:** `app.py`, Line 40: `app.run(port=9000, debug=True)`
- **Detailed Explanation:** When Flask runs with `debug=True`, the interactive Werkzeug debugger is enabled. In production or shared network environments, this console allows arbitrary Python code execution through the web browser upon encountering an unhandled exception. It also dumps system environment variables, local path layouts, and sensitive stack traces to client requests.
- **Priority:** High priority for remediation before release.

### Finding 2: Insecure Host Interface Binding
- **Rule ID:** `python:S8392` (*"Avoid binding the application to all network interfaces"*)
- **Category & Severity:** Security Vulnerability / Severity: Blocker (Software Quality: Security / Blocker Impact).
- **Location:** `app.py`, Line 45: `app.run(host="0.0.0.0", ...)`
- **Detailed Explanation:** Binding a development server to `0.0.0.0` listens on all available network adapters (including public Wi-Fi, Ethernet, and cloud VPC interfaces). Without an authenticating reverse proxy (such as Nginx) or TLS encryption, this exposes the lightweight development server to arbitrary external traffic.
- **Priority:** Critical blocker.

### Finding 3: Unrestricted Package Installation in CI Workflows
- **Rule ID:** `githubactions:S8541` (*"Omitting '--only-binary :all:' can lead to the execution of setup scripts. Make sure it is safe here"*) & `githubactions:S8544` (*"Using dependencies without locking resolved versions is security-sensitive"*)
- **Category & Severity:** CI/CD Security Vulnerability / Severity: Major (Software Quality: Security / Medium Impact).
- **Location:** `.github/workflows/sonarcloud.yml` (Line 29) & legacy `.github/workflows/ci.yml` (Lines 24–26).
- **Detailed Explanation:** Invoking `pip install` without restricting downloads to pre-compiled binary wheels (`--only-binary :all:`) allows pip to download source distribution archives (`.tar.gz`). During installation, arbitrary Python code contained within `setup.py` executes inside the CI runner environment, presenting supply-chain risks. Additionally, unpinned dependencies in legacy pipelines can cause non-deterministic builds.
- **Priority:** High priority for workflow hardening.

### Finding 4: Inadequate Exception Handling & Unmanaged Resources
- **Rule ID:** PEP 8 / Code Smells (`import-outside-toplevel`, unused variable `e`, resource descriptor leak).
- **Category & Severity:** Maintainability & Reliability / Severity: Minor.
- **Location:** `app.py` (Lines 31–33) and `model.py` (Line 14).
- **Detailed Explanation:** 
  1. `app.py` declared `except Exception as e:`, but variable `e` was never referenced.
  2. `import traceback` was nested inside the exception block, causing redundant module imports at runtime.
  3. `traceback.print_exc()` directed raw stack traces to standard error rather than using a structured logger.
  4. `model.py` performed `Image.open(img_path).convert("RGB")` without wrapping the stream in a context manager, leaving file descriptors uncollected.
- **Priority:** Medium priority for clean code hygiene.

## 6. Reflection & Critical Analysis (Part F)

### 6.1 Limitations of Static Code Analysis
While SonarQube Cloud successfully identified surface-level vulnerabilities (such as insecure debugging modes, interface bindings, and package manager flags), static analysis exhibits inherent limitations:
1. **Model Efficacy & Drift:** Static analysis evaluates Python code syntax, but cannot validate the algorithmic correctness or generalization accuracy of deep learning weights (`digit_model.h5`). It cannot detect whether predictions are biased or degrading.
2. **Adversarial & Numerical Vulnerabilities:** Static tools cannot detect subtle numerical stability issues (e.g., division by zero in tensor normalization or NaN propagation in activation functions) unless explicit rules exist.
3. **Runtime Execution Semantics:** Static scanners cannot simulate complex multi-threaded concurrency behavior, memory exhaustion under burst traffic, or dynamic race conditions. Automated dynamic testing (acceptance and stress testing) remains indispensable.

### 6.2 Independently Tested Risk: Malformed Payloads & Boundary Inputs
- **Identified Risk:** Processing unvalidated binary uploads can cause unhandled exceptions inside native C-extensions (PIL / LibTIFF / LibJPEG) or memory exhaustion when handling zero-byte or corrupted image streams.
- **Independent Test Strategy:** Created `test_acceptance_empty_filename` and `test_acceptance_missing_file` in `test_acceptance_sad.py`. We simulated requests with empty byte streams, missing files, and non-image buffers.
- **Verification:** The refactored exception handlers in `app.py` caught `ValueError` and `IOError` cleanly, logging an error and returning HTTP 200 with user-friendly error markup (`"File cannot be processed."`), preventing server-side process crashes.

### 6.3 Troubleshooting Problem and Resolution
- **Problem Encountered:** Upon initial setup, SonarQube Cloud's **Automatic Analysis** feature automatically triggered on repository import and produced an analysis with missing coverage data, conflicting with the GitHub Actions CI pipeline. Concurrently, SonarCloud's API endpoints rejected unauthenticated requests (`Authentication is required`), preventing manual status queries.
- **Root Cause:** SonarCloud enables Autoscan by default for newly imported GitHub repositories unless CI-based analysis is explicitly toggled. Autoscan does not execute `pytest` or generate `coverage.xml`.
- **Resolution:** 
  1. Utilized the authenticated SonarCloud API (`/api/autoscan/activation?enable=false`) with the generated user token to deactivate Automatic Analysis completely.
  2. Generated a dedicated project analysis token and saved it as repository secret `SONAR_TOKEN` via GitHub CLI (`gh secret set`).
  3. Configured `actions/checkout@v4` with `fetch-depth: 0` and `SonarSource/sonarqube-scan-action@v6` to run tests, produce `coverage.xml`, and upload metrics in a single authenticated, deterministic pipeline.
